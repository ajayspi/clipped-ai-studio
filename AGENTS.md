# Agent guide — clipped (Next.js 16 video studio)

> Authoritative for the `clipped` root app only. `omniroute-server/` is a **separate vendored project** (own deps/build/test, huge own `AGENTS.md`) — don't run its scripts, tests, or lint from root; the root `package.json` has none of them. `CLAUDE.md` → `@AGENTS.md`.

## Commands
Use **pnpm** (`packageManager: pnpm@11.24.0`; `pnpm-lock.yaml` canonical — ignore the stray untracked `package-lock.json`):
- `pnpm dev` — Next 16.3.3 + Turbopack on `:3000`
- `pnpm build` — standalone build (`next.config.ts` sets `output: 'standalone'`)
- `pnpm lint:scoped` — `eslint app lib components remotion scripts test tests` (**the usable lint**; root `pnpm lint` = `eslint .` → red-by-construction, see quirks)
- `pnpm typecheck` — `tsc -p tsconfig.check.json --noEmit` (via `tsconfig.check.json`, excludes vendored trees; **typecheck is NOT run by `build`** — `typescript: { ignoreBuildErrors: true }`; keep types clean manually)
- `pnpm exec vitest run` — unit tests (`test/**/*.test.{ts,tsx}`, jsdom; `test/setup.ts` mocks `@/lib/supabase/*`, `next/navigation`, fonts, fetch). **There is no `test:unit` script.**
- `pnpm test` / `pnpm test:e2e` — `node tests/e2e/standalone-runner.js` (zero-dependency runner, in-memory Supabase mock, **201 tests**: tiers 1–19 + API routes + workers). **Not the unit suite.**
- Verify order: `lint:scoped` → `typecheck` → `vitest run` → `test` → `build`.

## Repo quirks (verify before touching)
- **Two vendored OmniRoute trees exist.** `omniroute-server/` is the real, tracked one — used by `pnpm workers` and the app's AI gateway. `omniroute-server-untracked/` is an **untracked stale copy** (own `.git/`, `node_modules/`, own docs) — ignore it; never run, edit, or deploy from it.
- Root is littered with **untracked one-off deploy artifacts** (`deploy_*.py`, `*.zip`/`*.tar.gz`, `*.patch`, `build_out.txt`, `test_final*.txt`, …). Historical debris, not the deploy flow — don't read them as docs, don't clean the tree blindly (`0001-*.patch`/`patch.diff` are the same class).
- `.env.example`, `.env.local`, `.env.docker` are **all untracked**: `.gitignore` has a bare `.env*` with no `!.env.example` exception — a **fresh clone has no env file at all**. Tests don't care (`test/setup.ts` falls back to the remote Supabase project + mock keys); for dev copy `.env.example` from this checkout or ask the operator.
- `pnpm-workspace.yaml` uses pnpm 11's `allowBuilds` with **unfilled placeholder strings** (`set this to true or false`) for esbuild + `@ffmpeg-installer/linux-x64` — those build scripts currently don't run. That's the repo's current state; don't "fix" it. `pnpm install --frozen-lockfile` completes fine.
- `.gitignore` is ASCII but has a **UTF-16LE-encoded trailer** (`clipped_update.zip`, `next_build.tar.gz` rules) — the NUL bytes make the read tool / ripgrep treat it as binary. Use `git check-ignore -v <path>` to resolve ignore rules instead.
- **Root lint/tsc are red-by-construction; scoped commands are green (VERIFIED 2026-09-25).** `pnpm lint` = `eslint .` (only `.next/out/build/next-env.d.ts` in `globalIgnores`) → also lints the vendored `omniroute-server*` trees + root debris → **20,273 problems (14,057 errors)**. `pnpm exec tsc --noEmit` reads root tsconfig `include` → also globs the vendored trees → **Node OOM (exit 134, ~4GB heap)**. Both are repo-state issues, not code defects. Use `pnpm lint:scoped` + `pnpm typecheck` (via `tsconfig.check.json`, excludes `omniroute-server*`) — **green: 0 problems / exit 0** across app/lib/components/remotion/scripts/test/tests.
- `vitest run` under CPU contention (lint+tsc running) flakes with **fork-worker start timeouts** (`test/pages/create/mission.test.tsx` et al. — "Timeout waiting for worker to respond", not assertion failures); re-run the affected files alone when the machine is idle. **Deterministic fix (VERIFIED 2026-09-26): `pnpm exec vitest run --no-file-parallelism` — 189/189 green on this loaded machine.**
- **The vitest suite is flaky even with `--no-file-parallelism` and an idle box (MEASURED 2026-09-27).** 2 full runs each of baseline vs. a large change set, all on `--no-file-parallelism`: baseline failed 1 of 2 (on `library.test.tsx`), changed tree failed 1 of 2 (on `adversarial-boundary-m3.test.tsx`) — **the failing file differed between runs, and every failing file passes in isolation.** So a single failing full run is NOT evidence of a regression. To attribute a failure, run the file alone, and if it passes, re-run the full suite 2× before concluding anything.
- **`__dirname` is a STUB inside Next.js server bundles (VERIFIED 2026-09-27).** `lib/logger.ts` originally resolved its log dir from it; inside Turbopack it produced `C:\ROOT\logs\app.log`, so `/api/logs` returned a valid **HTTP 200 while reading a file that does not exist** — a silent wrong-file read, the worst failure mode for a logger. Under `tsx` (CJS) `__dirname` is correct, so worker-side tests all passed and hid it. Never use `__dirname` for filesystem paths in anything a Next route imports; probe for a real `package.json` or use `process.cwd()` (see `resolveRootDir` in `lib/logger.ts`).
- **`pnpm test` runs ONLY `tests/e2e/standalone-runner.js`.** The `tests/e2e/*.test.ts` files (`api-routes.test.ts`, `tier7-workers-e2e.test.ts`, …) are **not imported by anything** — they are dead. To add an e2e test, add a `tests.push({ tier, id, title, fn })` block to the runner **and** its tier name to the `tiers` array, or it will silently never execute. The runner's established style for cross-file contracts is reading the source and asserting on it (Tier 17/18/19), not importing TS.
- **`claim_render_job` selects on `orchestration_state`, NOT `status`, and the column DEFAULTs to `'queued'` — which is claimable.** A planning-only workflow that omits the field is silently picked up by the FFmpeg render worker, which builds an empty concat list (no `beats`) and burns all 3 attempts. Every route that inserts a planning-only or terminal job must set it explicitly (`'planning'` / `'completed'`). Guarded by Tier 20 (`T20-CLAIM-01/02/03`), which parses the claimable set out of `20260905_render_job_leases.sql` so it can't drift.
- **MEASURED 2026-09-28: no UI path in the app can actually render a video.** `app/api/v1/generate` is the **only** route that ever writes `orchestration_state: 'queued'` (its `after()` block flips `planning` -> `queued`), and **no page calls it** — it is the developer API, reached with an `Authorization: Bearer` key. Every route the UI *does* POST to is dead. (a) `app/api/workflows/generate` — the wizard's "Send to Queue" — never destructures `beats`/`aspectRatio`/`subject` and writes `orchestration_state` as an **object**, which is in neither `('queued','retryable')` nor the expired-lease set, so it is permanently unclaimable *and* the wizard's beats are thrown away; it still answers `200 {"success":true}`. Reproduced for all four wizard workflows (stories, ai-videos, footage, images). (b) `mission` and `whiteboard/character-sheet` leave the column **unset**, which defaults to the claimable `'queued'`, write **no `beats`**, and therefore make the worker build an empty `concat.txt` -> `ffmpeg ... Invalid data found when processing input` on all 3 attempts (reproduced live). (Note: `scrape` and `bulk-plan` do not insert into render_jobs at all, and the `images` route error path also omits orchestration_state). Tier 20 only guards the *insert* side, so it cannot see (b) — the failure there is "column left to its default", not a wrong value. **Rule: `claim_render_job` is the only definition of "this job will render"; a `200` from a workflow route means nothing. Assert claimability against the function, not against the response.**
- **The creation wizard hid its whole step flow with zero console errors (FOUND+fixed 2026-09-28).** Two independent causes, both silent — every route returned 200, every step rendered into the DOM, and the a11y tree looked complete:
  1. `CreationWizard`'s step card `<main>` was `flex flex-col` but its **only child was a bare `<div>`**; the header/body/footer wrapper and the `border-b` div holding them were plain blocks with default `min-height:auto`, so `flex-1 min-h-0` beneath them was inert, the card grew to its full content height, and its `overflow-hidden` clipped the body away. The Live Preview `<aside>` was an unbounded `shrink-0` column sibling below `lg`, taking its full ~850px natural height and starving the card to a **measured 1px** at y=1040 in a 527px viewport. **Rule: a flex child only sizes if every wrapper between it and the flex container is itself a shrinkable flex column — a bare `<div>` silently disables `flex-1`/`min-h-0`.**
  2. The step body was wrapped in `<AnimatePresence mode="wait">`, which must finish the outgoing child's exit before mounting the next. That exit never completed, so the old step stayed mounted — first measured at `opacity:0` + `translateX(20px)`. Removing `AnimatePresence` alone wasn't enough: `initial={{ opacity: 0 }}` on the keyed `motion.div` still made **visibility depend on the enter animation running**, and a later reload left all 5 steps at `opacity: 0` while every heading advanced correctly. **Rule: never gate content visibility on an animation completing — animate `transform` only, never `opacity` from 0, and never serialize a swap behind an exit animation.**
  - Both are guarded by Tier 21 (`T21-FLOW-01..05`), which asserts against the **markup with comments stripped** — the fix is explained in JSX comments right beside the code, so matching raw source makes the guard trip over its own docs and skip over code separated from the tag by a comment block.
  - **How to see this class of bug without a screenshot:** `getBoundingClientRect()` on the card, the aside, the scroll container, and the step content, plus `getComputedStyle(el).opacity` on the animated child. `innerText` is the *trap* here — it returns text from `opacity:0` and `overflow:hidden` subtrees, so an a11y/innerText snapshot reports a fully working step that is provably invisible. Always pair a text check with a geometry + opacity check.
  - Also removed: the hardcoded inline `maxHeight: 'calc(100vh - 14rem)'` on the step body, which assumed a fixed chrome offset and clipped the body into a ~300px window on short viewports. Flexbox owns that sizing.
  3. **(Desktop-only, and it is the one the user actually reported.)** The outer wrapper and the inner wrapper of `CreationWizard` carried **identical** classes `flex flex-col lg:flex-row flex-1 …`. HEAD has only ONE `lg:flex-row` (the inner one). The uncommitted rewrite added a second, so at `lg` the stepper's parent became a **row** while the stepper itself is `w-full` + `shrink-0` — i.e. `width: 100%` of the row with no shrink. The nav therefore consumed the entire row and pushed the card + Live Preview to **x=1464…2020, 580px past the right edge of a 1440px screen**: the whole 5-step wizard scrolled off-screen on desktop, and the nav itself stretched to 830px tall via `align-items: stretch`. **Rule: a `w-full` child with `shrink-0` is fine in a column and catastrophic in a row — check which axis a `w-full`/`h-full` is resolving against before adding a `flex-row` to an ancestor.** Fixed by dropping `lg:flex-row` from the outer wrapper (stepper stacks *above* the workspace; only the inner wrapper is a row at `lg`). Guarded by `T21-FLOW-06`, which walks back from the `<nav>` to its wrapper and that wrapper's parent and fails on any `lg:flex-row`. Verified at 1024/1100/1280/1440/1920.
  - **This bug was invisible from the devtools tab** because the controlled tab is 800×527 — *below* `lg`, where the stacked column layout is correct and everything measured fine. **There is no viewport-resize or device-emulation tool in this harness, and no `playwright` package in the repo (only a bare `ms-playwright/chromium-1243` binary).** To measure a desktop layout, host a **fixed-size same-origin `<iframe>`** — the iframe *is* its own media-query viewport, and you can read `contentDocument`/`contentWindow` and resize it to re-evaluate breakpoints with no reload: navigate the tab to a **non-React** same-origin page first (e.g. `/api/health`), because a React host gives you two Supabase clients and the iframe renders nothing (`Multiple GoTrueClient instances`, `bodyLen: 0`). Below `md` the app shell stops being viewport-constrained and the **document** scrolls instead of the shell, so "card extends past the fold" is not by itself a bug — check which of the two actually scrolls and whether the footer is reachable before calling it broken.
- **Tooling traps hit while fixing the wizard:** `browser.click` did **not** land on the `Continue` button, which looked exactly like a dead handler and cost a long false-positive hunt — dispatch the click in-page (`el.click()` / `new MouseEvent('click', {bubbles:true})`) via `browser.evaluate` and assert on the result instead. And `browser.evaluate` has a hard **60s** timeout, so a polling loop must be chunked across calls; a timed-out call's outcome is unknown, so re-read state rather than repeating the action. `location.reload()` inside `evaluate` often kills the call itself (`Inspected target navigated or closed`) — reload, then poll in a *separate* call.
- **zoompan camera moves must animate on `on`, NEVER `in` (FOUND+fixed 2026-09-28).** `buildZoompanFilter` (`lib/engine/ffprobe.ts`) drives every still's Ken Burns move from a `zoompan` expression. zoompan's `in` is the **INPUT** frame counter and does **not** advance while the filter generates output frames, so an `(in/...)` progress expression evaluates identically on every output frame and the shot renders as a **frozen still** — a valid mp4, `status: completed`, no error, indistinguishable from "the grade is dark" by eye. `on` (the **OUTPUT** frame counter) advances 0..N-1 and is the only correct variable. This bug was **live in production for the entire history of the feature** (the pre-existing `i % 2 ? 'in' : 'out'` alternation used `in` too), and it survived because the filter *string* reads fine and the white-source "no black edge" encode test is blind to motion. MEASURED on the worker's exact recipe: `in`-based moves render frame-to-frame MAD < 0.03 (frozen), `on`-based MAD > 11 (moving). **Rule: a camera-move filter is only proven by a real encode that measures the pixels changing between the first and last frame** — `test/camera-move-filter.test.ts` now does exactly that (textured `testsrc2` source, worker recipe, MAD thresholds) plus a string-level `not.toMatch(/\bin\b/)` guard. When a render "completes" but the beats don't move, suspect the zoompan variable before anything else.
